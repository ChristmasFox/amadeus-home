# PUBG V3.3 COMPLETION REPORT

## Architecture
V3.3 Fun Intelligence is an additive layer over the existing shared PUBG Prelude. It does not replace V3 QuerySubgraph or V3.2 ReviewSubgraph. The flow is:

```
MatchReviewFacts
  -> SpecialEvents
  -> KeyOperations
  -> FunCandidateGenerator / generateBaseFunEvents
  -> EventCombinationEngine
  -> FunEvent[]
  -> FunRanker
  -> Telegram  🤣 本局整活
```

Structured `FunEvent` remains the rendering contract; text is never used as a source of facts.

## FunEvent
Implemented `FunEvent` with `type`, `actorPlayerId`, `targetPlayerIds`, `factIds`, `evidenceIds`, `confidence`, `funScore`, `category`, `facts`, `tags`, `dedupGroup`, and `suppresses`. Every generated event carries fact IDs and evidence IDs and is filtered out if either is missing.

Confidence levels:
- `CONFIRMED`: direct team-damage/vehicle/rocket telemetry facts.
- `DERIVED`: combinations over confirmed/derived facts.
- `HEURISTIC`: supported by `FunRanker` but hidden by default.

## Team Damage
`team-damage.ts` extracts real friendly-fire hits only. Missed attacks are excluded. Sources are normalized as:
- `MELEE`, `GUN`, `VEHICLE`, `EXPLOSIVE`

Punch hits are kept separate from other melee hits so a pan cannot be presented as a punch. Pre-match and in-match phases remain separate.

## Punching
`TEAMMATE_PUNCHING` is generated from confirmed fist hits. Missed punches are not counted. Pre-match vs in-match phase is preserved.

## Vehicle
`extractTeamVehicleEvents` supports `HIT`, `KNOCK`, and `KILL` while keeping `driverConfirmed` independent of seat index. A driver-attributed joke is emitted only when driver status is confirmed. When unconfirmed, the renderer shows an un-attributed vehicle-damage fact.

`vehicle-intelligence.ts` keeps `rideDistance` and `driveDistance` separate. `driveDistance` is only increased when `driverConfirmed` is true. Distance alone is not turned into a key operation.

## Flash
Flash usage is counted from `ATTACK`/`THROWABLE_USE` with attackId/time deduplication. `FLASH_TEAMMATE`/`FLASH_ENEMY` are deliberately not invented because current telemetry evidence is insufficient.

## Heavy Weapon
`heavy-weapon-intelligence.ts` uses `LogPlayerAttack` + `attackId` for shots, ignoring aggregate `LogWeaponFireCount.fireCount`. Hits are deduplicated by attackId and target. Vehicle damage/destroy counts are tracked separately.

Supported rocket events:
- `ROCKET_UNUSED`
- `ROCKET_ALL_MISS` / `ROCKET_MISS`
- `ROCKET_HIT`
- `ROCKET_VEHICLE_DESTROY`
- `ROCKET_MULTI_KILL`
- `ROCKET_VEHICLE_MULTI_KILL`

`ROCKET_VEHICLE_MULTI_KILL` requires weapon-causal destroy evidence and matching vehicleId/attackId. Time proximity alone is not sufficient.

## Combat / Support Fun
`fun-event-generator.ts` emits evidence-backed combat/support events including `HIGH_DAMAGE`, `LOW_DAMAGE`, `HIGH_KNOCK_LOW_KILL_CONVERSION`, `LOW_DAMAGE_HIGH_KILLS`, `NO_COMBAT_PRESENCE`, `MOST_REVIVES`, and `MOST_ASSISTS`.

Commentary now supports real negative or neutral outcomes. A player with no combat/contribution is reported as such instead of being given a manufactured positive role.

## Event Combination
`EventCombinationEngine` combines structured facts through deterministic configurable rules. Current rules:
- `first_punch_then_fight`: punch hits + low enemy damage -> `🥊 先礼后兵`
- `punch_and_vehicle_damage`: confirmed punch + confirmed vehicle team damage -> `🚨 友军威胁`
- `tourist_bus`: high ride distance + zero/low combat -> `🚌 PUBG旅游团`
- `rocket_reserve`: multiple rocket pickups + zero shots -> `🎒 战略储备`
- `revive_failure`: many revives + non-win placement -> `🩺 人救麻了`
- `attack_direction`: friendly fire is a significant share of enemy damage -> `🎯 攻击方向值得研究`

Combos suppress covered single events via `suppresses`.

## Scoring / Dedup
`FunRanker`:
- hides `HEURISTIC` events by default
- filters events without facts/evidence
- sorts by funScore, evidence count, then stable IDs
- prefers distinct actors/types in the first pass
- applies `dedupGroup` and `suppresses`

Output is limited to the configured default (5) and falls between 2 and 5 when sufficient candidates exist.

## Telegram UX
`buildReviewPresentation` consumes `analysis.funEvents` and renders the `fun` section as `🤣 本局整活`, replacing the legacy `🎲 趣味记录`. Events are selected per review profile; no markdown wide tables are used.

## Known Limitations
- Flash victim events (`FLASH_TEAMMATE`, `FLASH_ENEMY`) are not generated because the current telemetry normalization has no reliable victim evidence.
- Driver status is confirmed only from explicit telemetry signals; seatIndex alone is not trusted.
- Fun candidates generated from legacy `funCandidates` remain available for backward compatibility, but the Telegram renderer uses `funEvents`.
