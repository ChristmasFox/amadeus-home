# Amadeus 1.8.0 — single-reference image route deployed

Date: 2026-10-01 (Asia/Shanghai)
Status: `DEPLOYED_AUTOMATED_GATES_PASSED_MANUAL_OWNER_REFERENCE_IMAGE_ACCEPTED`

## Root cause

Amadeus 1.7.9 correctly forced `openai/amadeus-image`, but a request carrying
one reference image entered pinned OpenClaw's native OpenAI adapter edit branch.
That branch sent multipart to `/v1/images/edits`. The live 9Router 0.5.91
route manifest contains `/api/v1/images/generations` but no `/api/v1/images/edits`.
A content-free multipart probe reproduced HTTP 500 and the supplied Next.js
`Failed to find Server Action` error. Prompt-only requests used generations and
succeeded. This was not a model-override escape or browser cache issue.

## Fix

Source commit `2244f98` adapts exactly one PNG/JPEG/WebP reference, up to 10 MiB,
into the existing logical `openai/amadeus-image` JSON generations request. The
same bytes are retained for both Combo attempts: the exact Codex adapter maps
them to `input_image`; the exact Antigravity/Gemini adapter maps them to
`inlineData`. The existing primary/fallback order and 9Router accounts,
credentials, Combo, and source remain unchanged. Multi-reference input fails
closed before task admission; no reference is dropped and no edit request is
sent to the nonexistent endpoint. Other configured providers retain their
native multipart edit path.
