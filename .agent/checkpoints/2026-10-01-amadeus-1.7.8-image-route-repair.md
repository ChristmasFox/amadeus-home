## Why the 1.7.7 retry still failed

The owner retried the private WhatsApp image flow on 1.7.7. A content-safe audit
confirmed `before_tool_call` ran, but the native tool result still carried the
concrete `openai/gpt-image-2` model and the OpenAI-compatible provider returned
HTTP 400 `invalid_request_error/bad_request`.

The exact pinned OpenClaw 2026.9.4 hook implementation shallow-merges returned
hook params over original params. Returning a params object that omitted `model`
did not remove the original key. 1.7.8 now sets the override to an empty string;
the native parser treats blank as no model override, while schema validation
still accepts it. The configured `openai/amadeus-image` logical capability and
9Router fallback are then selected. Regression tests reproduce the host merge
and assert the blank sentinel survives it.

The same trace showed `request_language=unknown`. Read-only state-database
comparison showed the task requester session key matched the inbound WhatsApp
session. Source review found `event.body ?? event.content` could select a
present-but-blank body and never try non-empty normalized content. 1.7.8 now
chooses the first non-empty string; regression coverage uses blank body plus
Chinese/Japanese `content`.

No rollback was performed. No private user message, prompt, or image is included
in this checkpoint.
