# 2026-09-24 — 9Router native speech alias lifecycle fixture

- Tested the repository-built `0.5.81` ARM64 candidate and a temporary evaluation image with `9router@0.5.86` against independent network-none data/keys; neither touched the live 9Router container or provider DB.
- The fixture used dashboard API login, a fixture-only API key, Self-hosted STT/TTS provider connections and aliases, and real ffmpeg-generated WAV bytes. TTS `amadeus-tts` immediately reached the mock OpenAI-compatible service with `model=qwen3-tts-1.7b`, `voice=kurisu-v1` and returned fixture MP3. Direct `selfhosted-stt/qwen-audio-3.0-asr-flash` reached the bridge and returned the expected no-network `provider_unavailable`.
- **Critical distinction:** `amadeus-asr` alias immediately after creation returned HTTP 400 `No credentials for provider: openai` despite the stored alias and no Chat Combo. This occurred in both package versions. After a 9Router process restart with the same isolated DB, `amadeus-asr` reached the bridge and returned the expected structured `provider_unavailable`. Thus a provider/model alias exists in storage but the pinned STT route may retain a stale alias view until restart; a dashboard write alone cannot prove STT routing.
- Updated the source-controlled provisioning script to preflight both bridge and M204 TTS health before any dashboard write, then restart 9Router once after aliases and verify dashboard/bridge health plus protected API-key 401. Offline tests cover gate, restart success and failure. The isolated test now asserts the post-restart alias path rather than claiming the initial 400 is success.
- Temporary evaluation image was not used for production; the repository still pins `9router@0.5.81` because `0.5.86` did not fix this STT alias lifecycle. The live 9Router/OpenClaw Compose and `VERSION=1.5.2` remain unchanged. DashScope key/region URL and real audio acceptance are still missing.
