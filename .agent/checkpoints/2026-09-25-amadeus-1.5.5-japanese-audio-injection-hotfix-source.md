# 2026-09-25 — Amadeus 1.5.5 Japanese voice-audio injection hotfix (source)

## Failure evidence and diagnosis

- Owner reported Japanese voice-audio policy still produced Chinese speech after 1.5.5 formal release.
- Read-only sanitized trace of the latest WhatsApp voice run showed assistant final output as Chinese-only: no `日本語：` line and no `[[tts:text]]`. No user or assistant text was copied to Git.
- The exact pinned OpenClaw 2026.9.4 `message_received` mapper (`toPluginMessageContext`/`deriveInboundMessageHookContext`) does not include `runId`; existing `VoiceReplyTurnTracker.record` rejected the event because it required a runId. Thus the voice Skill wasn't scoped/injected for the failed run, explaining why the model followed the Chinese language request and native inbound TTS spoke Chinese.

## Source fix

- Tracker now accepts a verified WhatsApp audio event with a `sessionKey` when the pinned message_received mapper omits runId.
- The pending marker is bound to the actual runId at `before_prompt_build`; a different run in that session will not inherit the bound marker.
- `agent_end` clears the run/session marker. Existing WhatsApp/audio-only gate, TTL (10 minutes), max entries (128) and typed-only behavior remain.
- Regression tests simulate the real pinned shape (no runId in message_received event or context), assert Japanese voice Skill injection on the subsequent run, and assert typed-only no-leak after cleanup.
