# 2026-09-25 — Consecutive voice followup TTS fix source candidate

## Root cause

Pinned OpenClaw 2026.9.4 core `sendFollowupPayloads()` takes the direct originating-channel `routeReply()` path for same-channel followups. It does not apply the standard final auto-TTS pipeline. In the user-reported group sequence, two Ogg inputs and two assistant final turns were persisted but only one media send was logged; this is consistent with one response taking the direct core followup route and remaining text-only.

## Source fix

- Added WhatsApp monitor ingress FIFO in `patch-openclaw-whatsapp-voice-lifecycle.mjs`. It wraps the pinned `createWebOnMessageHandler.processForRoute` boundary, waits only when the same session has a live voice lease or a voice-scoped tail, then replays queued items through ordinary `processMessage` / `runChannelInboundEvent`.
- Every queued audio message receives its own composing lease before its Agent run, so it traverses the normal TTS and WhatsApp PTT delivery path. Same-session later text remains FIFO behind queued voice. Typed-only sessions bypass the queue.
- A transient composing-presence error stops refresh but keeps the voice queue lock until full-turn settlement, disconnect, or the 120-second fallback; it no longer lets a later voice steer/run before the current TTS settles.
- Existing core queue patch remains a defensive fallback; ordinary monitor-routed WhatsApp arrivals are held before reaching that followup delivery path.
