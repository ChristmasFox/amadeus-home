# PUBG V3.2 — Review Data Model

## Store Separation

| Store | Owner | Contents | Used by |
| --- | --- | --- | --- |
| Match Store (`pubg_cache`) | n8n Data Gateway/Sync | normalized Match metadata and player summary statistics | V3 QuerySubgraph + review candidate picker |
| Context Store (`state.json`) | Runtime | sender-scoped selectors, ResultSet references and active Match | shared Prelude + follow-up routing |
| ResultSet Store (`state.json`) | Runtime | query rows, Match IDs, coverage, source and TTL | shared V3 follow-up and Picker source set |
| Telemetry Feature Store (`features.json`) | TypeScript Worker | parser/versioned derived review facts and evidence | V3.2 ReviewSubgraph only |
| Selection Store (`selections.json`) | Runtime | short callback token to Match binding | Telegram callback resume |

Ordinary `report`, `rank`, `strongest`, `weakest`, `compare` and `trend` never call the Telemetry Feature Store or download telemetry.

## MatchReviewFacts

The durable review object is structured data, not a final string:

```ts
interface MatchReviewFacts {
  schemaVersion: 1;
  match: ReviewMatchSummary;
  squad: ReviewSquadSummary;
  players: ReviewPlayerFacts[];
  combat: { eventCount: number; damage: number; knocks: number; kills: number; revives: number; events: NormalizedTelemetryEvent[] };
  fights: Fight[];
  weapons: WeaponStats[];
  vehicles: VehicleStats[];
  heavyWeapons: HeavyWeaponStats[];
  specialEvents: SpecialEvent[];
  evidence: ReviewEvidence[];
}
```

Facts are tagged by semantic layer:

- `FACT` — values read from Match Store or explicitly normalized from telemetry.
- `DERIVED` — deterministic fights, operations, aggregates and event correlations.
- `ANALYSIS` — explanatory conclusions generated from Facts.
- `FUN` — optional presentation-safe observations such as unused rockets or long drives.

FACT values are not rewritten by an LLM. Every derived key operation, fight and special event carries `evidenceIds`; claims such as rocket vehicle multi-kill require explicit attack/vehicle/kill correlation, not time proximity alone.

## Telemetry Lifecycle

```text
matchId + parserVersion + featureVersion
        ↓
Feature cache HIT → derived MatchReviewFacts
        │
        └─ MISS → download → gzip decode → normalize → correlate
                         → fight/operation/vehicle/weapon extraction
                         → persist derived facts
```

The normalized event stream is transient. JSON Feature Store writes compact facts and evidence references only; `combat.events` is retained as an empty typed collection after persistence. The pre-compaction file is recoverable at `/DATA/AppData/pubg-query-engine-v3/backups/features-before-compaction-20260903.json`.

## Feature Versioning

Each cache record is keyed by:

```text
matchId : parserVersion : featureVersion
```

Changing parser behavior or adding feature families can use a new version and reprocess without treating stale features as current. Current live values are `telemetry-parser-3` and `review-features-3`; older versioned records remain available for rollback and comparison.

## Presentation Boundary

`MatchReviewResult` contains `facts`, `analysis` and telemetry status. `ReviewPresentation` maps it to Sections (`overview`, `players`, `key_operations`, `key_fights`, `turning_points`, `weapons`, `vehicles`, `heavy_weapons`, `fun`, `conclusion`). `TelegramRenderer`/`KOOKRenderer` then handles text length and platform buttons. No detector depends on the final text template.
